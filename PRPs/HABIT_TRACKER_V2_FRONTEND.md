# Habit Tracker V2 — Frontend Redesign (ShadCN)

## Status: Draft for review
Builds on `habit-tracker-api/PRPs/HABIT_TRACKER_V2_SPEC.md` and
`habit-tracker-api/PRPs/HABIT_TRACKER_V2_SCHEMA_API.md`. Read those first —
this doc assumes the Goal → Habit → Task model and REST surface defined
there, and designs the `habit-tracker-app` changes needed to consume it.

## 0. Why this isn't a patch

The current app (`PRPs/habit-tracker-frontend.md`) is built entirely around
the v1 shape: flat `Habit` (name, description, frequency: daily/weekly/
custom, category, color) + per-habit `HabitGoal` (targetFrequency,
weekly/monthly/yearly) + `HabitTracking` log entries. None of those fields
or relationships exist in V2. This is a rewrite of the data layer and the
primary screens, not an incremental change. Auth (`authStore`, `authService`,
`tokenStorage`, the axios interceptor in `services/api.ts`) is untouched —
the V2 API keeps the same JWT pattern.

## 1. Stack Changes

| Area | Before | After | Why |
|------|--------|-------|-----|
| UI components | Hand-rolled (`components/common/*`) | [shadcn/ui](https://ui.shadcn.com) on Radix primitives | Per request — accessible primitives, consistent styling, no more bespoke `Button`/`Select`/`Modal` |
| Routing | None (single view swapped in `App.tsx`) | `react-router-dom` | V2 is a real hierarchy (Goals → Goal detail → Habit detail); v1's flat habit list had nothing to drill into |
| Forms | Manual `useState` + manual validation | `react-hook-form` + `zod` | Pairs natively with shadcn's `Form` component; needed for the SUM vs THRESHOLD_COUNT conditional validation in §4 |
| Server state | Zustand stores doing fetch+cache+mutate | **Kept as Zustand** (`goalStore`, `habitStore`, `taskStore`) | Matches existing codebase convention; introducing TanStack Query on top would be swapping a working pattern for no requirement-driven reason |
| Toasts/errors | Inline `{error && <div>}` per component | `sonner` (shadcn's recommended toast) | Centralizes async error/success feedback |
| Date handling | `date-fns` | Unchanged | Still fine; see §6 gotcha on timezone handling |

No changes to: `vite.config.ts` PWA block, Tailwind v4 setup, `axios` instance,
auth flow.

## 2. ShadCN Setup

```bash
npx shadcn@latest init
```

Tailwind v4 note: this repo has no `tailwind.config.js` (v4 CSS-first setup).
shadcn's CLI (v2.something+) supports this — it detects the `@import
"tailwindcss"` in `src/index.css` and writes CSS variables into a `@theme
inline` block there instead of a JS config. Do **not** let it scaffold a
`tailwind.config.js`; if it offers to, decline — v4 doesn't use one (same
gotcha the original PRP already flagged for the base Tailwind setup).

`components.json` config:
- Style: `new-york`
- Base color: `slate` (neutral, works with the existing gray/indigo gradient
  aesthetic in `index.css` rather than fighting it)
- CSS variables: yes
- Path aliases: `@/components`, `@/lib/utils`, `@/hooks` — requires adding
  the `@` → `src` path alias to `tsconfig.app.json` and `vite.config.ts`
  (`resolve.alias`), since neither currently defines one.

Components to add (install only what's used, not the whole catalog):

```bash
npx shadcn@latest add button card dialog alert-dialog form input label \
  select tabs badge progress popover toggle-group switch separator \
  skeleton sonner dropdown-menu
```

- `toggle-group` → the Mon–Sun `frequencyDays` picker.
- `switch` → Task done/not-done toggle on the Today card.
- `alert-dialog` → delete confirmations (Goal/Habit delete, both cascade —
  needs an explicit "this deletes N habits / all tasks" warning).
- `sonner` → replaces every ad-hoc `error`/`loading` string currently stored
  in Zustand state for user-facing feedback (keep `loading` booleans for
  skeletons, drop `error` strings in favor of toast calls).
- No `calendar` primitive — the task calendar grid is a custom component
  (§5.4), since it needs per-cell status coloring and disabled/unscheduled
  states that shadcn's date-picker-oriented `Calendar` isn't built for.

`src/lib/utils.ts` (the `cn()` helper) is generated by the CLI automatically
and used everywhere instead of manual template-literal class concatenation.

## 3. Types (`src/types/`)

Delete `tracking.ts` and the old `goal.ts`/`habit.ts` contents entirely —
replace with:

```typescript
// src/types/goal.ts
export interface Goal {
  id: string
  title: string
  startDate: string   // YYYY-MM-DD
  endDate: string      // YYYY-MM-DD
  unifiedProgress: { current: number; target: number } | null
  habits: HabitSummary[]
  createdAt: string
  updatedAt: string
}

export interface CreateGoalDto {
  title: string
  startDate: string
  endDate: string
}

export type UpdateGoalDto = Partial<CreateGoalDto>
```

```typescript
// src/types/habit.ts
export type HabitGoalType = 'sum' | 'threshold_count'

export interface HabitSummary {
  id: string
  name: string
  unit: string | null
  goalType: HabitGoalType
  targetValue: number | null
  dailyMinValue: number | null
  targetDays: number | null
  frequencyDays: number[]      // 0=Sun..6=Sat
  defaultTaskValue: number | null
  progress: { current: number; target: number }
  currentStreak: number
  longestStreak: number
}

export interface Habit extends HabitSummary {
  goalId: string
  createdAt: string
  updatedAt: string
}

interface HabitBaseDto {
  name: string
  unit?: string | null
  frequencyDays: number[]
  defaultTaskValue?: number | null
}

export type CreateHabitDto = HabitBaseDto &
  (
    | { goalType: 'sum'; targetValue: number; dailyMinValue?: never; targetDays?: never }
    | { goalType: 'threshold_count'; dailyMinValue: number; targetDays: number; targetValue?: never }
  )

export type UpdateHabitDto = Partial<CreateHabitDto>
```

```typescript
// src/types/task.ts
export type TaskStatus = 'done' | 'not_done'

export interface Task {
  id: string
  habitId: string
  date: string            // YYYY-MM-DD
  value: number | null
  status: TaskStatus
  completedAt: string | null
}

export interface UpsertTaskDto {
  value?: number | null
  status?: TaskStatus
}
```

The discriminated union on `CreateHabitDto` is the main payoff of switching
to zod/react-hook-form: the same union becomes the zod schema in §4, and
TypeScript rejects a `sum` habit with `dailyMinValue` set at compile time.

## 4. Services + Stores

### 4.1 Services — `src/services/`

Replace `habitService.ts`, add `goalService.ts` and `taskService.ts`, delete
`trackingService.ts`. Pattern matches the existing `habitService.ts`
(unchanged `apiClient` import):

```typescript
// src/services/goalService.ts
export const goalService = {
  list: () => apiClient.get<Goal[]>('/goals').then(r => r.data),
  get: (id: string) => apiClient.get<Goal>(`/goals/${id}`).then(r => r.data),
  create: (data: CreateGoalDto) => apiClient.post<Goal>('/goals', data).then(r => r.data),
  update: (id: string, data: UpdateGoalDto) => apiClient.put<Goal>(`/goals/${id}`, data).then(r => r.data),
  remove: (id: string) => apiClient.delete(`/goals/${id}`),
}
```

```typescript
// src/services/taskService.ts
export const taskService = {
  listRange: (habitId: string, from: string, to: string) =>
    apiClient.get<Task[]>(`/habits/${habitId}/tasks`, { params: { from, to } }).then(r => r.data),
  today: (habitId: string) =>
    apiClient.get<Task>(`/habits/${habitId}/tasks/today`).then(r => r.data), // throws 404 if unscheduled
  upsert: (habitId: string, date: string, data: UpsertTaskDto) =>
    apiClient.put<Task>(`/habits/${habitId}/tasks/${date}`, data).then(r => r.data),
}
```

`habitService.ts` gains `goalId` in `create`/`list` paths per §5.2 of the
API doc (`/goals/:goalId/habits`), keeps `get`/`update`/`delete` flat under
`/habits/:id`.

### 4.2 Stores — `src/store/`

Three stores replacing `habitStore.ts`/`goalStore.ts`/`trackingStore.ts`:

- **`goalStore.ts`**: `goals: Goal[]`, `fetchGoals`, `createGoal`, `updateGoal`,
  `deleteGoal` — same shape as the existing `habitStore.ts` pattern (loading
  bool, optimistic-free refetch-after-mutate).
- **`habitStore.ts`**: scoped to *one* goal's habits at a time —
  `habitsByGoalId: Record<string, HabitSummary[]>`, `currentHabit: Habit | null`,
  `fetchHabitsForGoal(goalId)`, `fetchHabit(id)`, `createHabit(goalId, dto)`,
  `updateHabit(id, dto)`, `deleteHabit(id)`. On `updateHabit` success, also
  invalidate any cached task range for that habit (§5 side effect: BE deletes
  `NOT_DONE` tasks on habit edit, so a stale FE calendar would show ghost
  entries) — simplest fix is `taskStore.clearRangeCache(habitId)`.
- **`taskStore.ts`**: `tasksByHabitId: Record<string, Task[]>`, `todayByHabitId:
  Record<string, Task | 'unscheduled'>`, `fetchRange(habitId, from, to)`,
  `fetchToday(habitId)` (catches 404 → stores `'unscheduled'`), `upsertTask
  (habitId, date, dto)` — on success, patches both the range cache and the
  today cache if `date` matches today, **and** calls `habitStore.fetchHabit
  (habitId)` to pull the recalculated `currentStreak`/`longestStreak` (the API
  recomputes streak server-side on every `PUT`, per API doc §5.3 — the FE
  must not try to recompute it locally).

All three use `sonner.error(...)` in catch blocks instead of setting an
`error` string in state.

## 5. Routing & Screens

Add `react-router-dom`. New route tree in `App.tsx` (auth gate stays
identical — `AuthContainer` short-circuits before the router mounts):

```
/                        → redirect to /goals
/goals                   → GoalListPage (dashboard)
/goals/:goalId           → GoalDetailPage
/habits/:habitId         → HabitDetailPage
```

### 5.1 `GoalListPage`

Grid of `GoalCard` (shadcn `Card`). Each card:
- Title, date range (`startDate`–`endDate` formatted with `date-fns`).
- If `unifiedProgress` is non-null: one shadcn `Progress` bar + "`current`/`target`".
- If `unifiedProgress` is null: stacked mini-rows, one per habit, each a
  small `Progress` + habit name (matches API doc §5.4 example response) —
  no single number, by design (spec §3.3).
- "New Goal" button → `Dialog` with `GoalForm` (title + start/end date
  inputs via shadcn `Input type="date"`, zod: `endDate >= startDate`).
- Card click → `/goals/:goalId`.

### 5.2 `GoalDetailPage`

- Header: title, date range, edit/delete (delete → `AlertDialog`, copy warns
  "This deletes N habits and all their tracked tasks").
- `unifiedProgress` banner if present.
- List of `HabitCard` (name, unit, goalType badge, `Progress`, streak pair —
  see §5.3) each linking to `/habits/:habitId`.
- "Add Habit" button → `Dialog` with `HabitForm` (§5.3).

### 5.3 `HabitForm`

Built with shadcn `Form` + `react-hook-form` + `zod`, mirroring the
`CreateHabitDto` discriminated union from §3:

```typescript
const habitSchema = z.discriminatedUnion('goalType', [
  z.object({
    goalType: z.literal('sum'),
    name: z.string().min(1),
    unit: z.string().nullable().optional(),
    targetValue: z.coerce.number().positive(),
    frequencyDays: z.array(z.number().int().min(0).max(6)).min(1, 'Pick at least one day'),
    defaultTaskValue: z.coerce.number().optional(),
  }),
  z.object({
    goalType: z.literal('threshold_count'),
    name: z.string().min(1),
    unit: z.string().nullable().optional(),
    dailyMinValue: z.coerce.number().positive(),
    targetDays: z.coerce.number().int().positive(),
    frequencyDays: z.array(z.number().int().min(0).max(6)).min(1, 'Pick at least one day'),
    defaultTaskValue: z.coerce.number().optional(),
  }),
])
```

UI: `Tabs` or `Select` to pick `goalType` (sum / threshold_count — displayed
as "Total target" / "Daily minimum, X days"), which conditionally renders
`targetValue` vs. `dailyMinValue`+`targetDays` fields. `frequencyDays` is a
7-item `ToggleGroup type="multiple"` (Sun..Sat labels, values 0-6).

Editing an existing habit: show a one-line warning ("Unscheduled tasks will
be regenerated under the new rules; completed tasks are untouched") per API
doc §5.2 side effect — this is non-obvious backend behavior the user should
know about before confirming an edit.

### 5.4 `HabitDetailPage`

- Header: name, unit, goalType, streak pair as two stat `Card`s (flame icon
  from `lucide-react`, current vs. longest) — replaces old `StreakDisplay`.
- `TaskTodayCard`: calls `taskStore.fetchToday(habitId)`.
  - If `'unscheduled'`: muted card, "Not scheduled today".
  - If a `Task`: numeric `Input` for `value` — **always shown**, regardless
    of `unit`. `unit` is only a display label (e.g. "km"); both `SUM`
    (sums `value`) and `THRESHOLD_COUNT` (compares `value` against
    `dailyMinValue`) need a value either way, so hiding the field for a
    unit-less habit silently stranded `THRESHOLD_COUNT` progress at 0
    forever (see §10 item 5 for how this was found). Pre-filled from
    `task.value`, else `defaultTaskValue`, else — for `THRESHOLD_COUNT` —
    `dailyMinValue`, so toggling "Done" with no edits qualifies by default.
    A `Switch` handles status; toggling to done (or blurring a changed value
    while already done) calls `taskStore.upsertTask`.
- `TaskCalendarGrid` (replaces `TrackingCalendar`): month grid, fetches via
  `taskStore.fetchRange(habitId, monthStart, monthEnd)` — **only the visible
  month**, not the full goal period (see §6, resolves API doc open item #1
  from the frontend side: request narrow ranges, let lazy-creation handle
  the rest on scroll/navigate).
  - Cell states: `done` (filled, habit-colored... actually no per-habit
    color anymore since `color` field is dropped — use a single accent,
    e.g. `bg-primary`), `not_done` + past (muted red outline), `not_done` +
    future/today (neutral), **not in `frequencyDays`** (disabled, no click
    handler, dimmed — per API doc open item #2, assume `PUT` 404s on
    off-schedule dates, so don't let the UI attempt it).
  - Clicking a scheduled, non-disabled cell opens a small `Popover` with the
    value input + done/not-done switch (same control as `TaskTodayCard`,
    extracted as a shared `TaskEditor` component used by both).

## 6. Day-Boundary / Date-String Gotcha (carried over from backend doc §3)

The API treats `date`, `startDate`, `endDate` as plain `YYYY-MM-DD` strings
and resolves "today" using a fixed Vietnam-time (UTC+7) boundary — not the
browser's local timezone. The FE must not round-trip these through
`new Date(dateString)` for *comparison* logic (e.g. "is this cell today?"),
because `new Date('2026-10-16')` parses as UTC midnight and can shift a day
in browsers west of UTC. Rules:
- Compare dates as strings (`date === todayString`) or via
  `date-fns/parseISO` + `isSameDay` only for *display formatting*, never for
  determining "is this today" — ask the API's `tasks/today` endpoint for
  that instead of computing it client-side.
- Format `startDate`/`endDate`/`date` for display with
  `format(parseISO(dateStr), 'MMM d, yyyy')`, fine since that's pure
  rendering, not boundary logic.
- `currentStreak`/`longestStreak` are never recomputed client-side (§4.2) —
  this sidesteps needing the VNT grace-period logic in the FE at all.
- **Future dates are rejected server-side** (`PUT .../tasks/:date` → `400`,
  `"<date> is in the future and cannot be completed yet"` — not part of the
  original spec/API doc, confirmed during backend data-integrity cleanup).
  `TaskCalendarGrid` detects "future" without computing "today" client-side:
  `listRange` only creates/returns rows for scheduled dates up to and
  including the server's today, so once a month's range fetch has resolved,
  a scheduled date with no row back is necessarily in the future — disable
  that cell using absence-of-a-row, not a local `new Date()` comparison. The
  `400` rejection (surfaced via the existing toast error path) is the
  backstop for the brief window before a range fetch resolves, or for any
  interaction this heuristic doesn't catch.

## 9. Validation Gates

```bash
npx tsc --noEmit
npm run build
npm run preview
```

Manual QA pass:
1. Create a Goal, add two Habits with the **same** `unit`+`goalType` →
   `unifiedProgress` renders as one bar on `GoalListPage`/`GoalDetailPage`.
2. Add a third Habit with a different `unit` to the same Goal →
   `unifiedProgress` becomes `null`, UI falls back to per-habit rows.
3. Create one `sum` habit and one `threshold_count` habit → form correctly
   switches required fields; both validate and submit.
4. On `HabitDetailPage`, mark today's task done with a value for a `sum`
   habit → `TaskTodayCard` and `TaskCalendarGrid` both update, streak stat
   increments.
5. Visit a date outside `frequencyDays` in the calendar → cell is disabled,
   no click handler fires.
6. Edit a habit's `frequencyDays` → confirm the warning copy shows, and
   previously-visible `not_done` future cells disappear/regenerate correctly
   on next fetch.
7. Delete a Goal with habits/tasks → `AlertDialog` warning shown, cascade
   confirmed (goal disappears from list).
8. Resize to mobile width — `ToggleGroup` day picker and calendar grid stay
   usable at ~375px (touch targets ≥44px, same bar the old PRP set).

## 10. Open Items (carried from / affecting backend doc §6)

1. Backend open item #1 (full-range vs. visible-range task creation) — FE
   commits to requesting only the visible month (§5.4). If backend later
   caps ranges, no FE change needed; if backend only supports full-range
   eager creation, revisit `TaskCalendarGrid`'s fetch granularity.
2. Backend open item #2 (404 on off-schedule `PUT`) — FE assumes this and
   disables those cells preemptively. If backend instead allows ad-hoc
   off-schedule logging, the disabled-cell behavior in §5.4 needs to flip to
   "enabled but visually distinct."
3. No offline/PWA caching strategy is defined for the new `/goals`,
   `/habits`, `/tasks` routes — the existing `vite-plugin-pwa` `NetworkFirst`
   `/api/.*` runtime-caching rule in `vite.config.ts` still applies as-is,
   not revisited here.
4. **Resolved**: a "can a task be completed ahead of its scheduled date"
   rule was not in the original spec/API doc. Confirmed during backend
   data-integrity cleanup (two invalid future-dated rows found on a test
   account) that the API rejects it outright — see §6. `TaskCalendarGrid`
   now disables future cells accordingly.
5. **Known gap, not fixed here**: for a `threshold_count` habit, `status:
   done` (which drives the streak) and `value >= dailyMinValue` (which
   drives progress) are independent — a day can be "done" and streak-worthy
   while not qualifying toward progress, if its `value` is `null`/too low.
   `TaskEditor` now always collects a value (defaulting to `dailyMinValue`
   when none is set, so a plain toggle qualifies by default — see §5.4's
   `TaskEditor` notes), which prevents *new* zero-value completions, but a
   habit's *historical* done-but-unqualified days are not retroactively
   fixed — completed tasks are intentionally never auto-modified (spec §8).
